    Chapter 01 · Method

    From a vague wish to twelve falsifiable decisions

    The starting point was a feeling: score has good math and no home for its data, and I want to learn systems programming. A feeling can't be reviewed. A decision with a stated alternative and a stated reason to reverse it can.

    Learning goals
    • Run a grilling session: one question at a time, each with a recommended answer to accept or reject.
    • Order questions by how much they constrain: why and who before how, formats last.
    • Write each decision so an observation could prove it wrong.
    • Use Parnas's information-hiding criterion to decide where the interfaces go.

    Where the project stood

    score already computed log-returns, Sharpe ratios and maximum drawdown in C++23 with nanobind bindings. Three things were missing. There was no persistence: data arrived on two disconnected paths, live yfinance pulls in src/score/market.py and a synthetic geometric-Brownian-motion generator in scripts/gen_mock_data.py, and neither was stored. There was no VaR or CVaR, which is what a trading desk means by "risk". And there was no networking or concurrency code at all.

    The grilling method

    A grilling session is a structured interview. The interviewer asks one question, proposes a recommended answer, and waits. The person either accepts, rejects, or amends it, and the interviewer moves to the next question only when the answer is specific enough to act on. Three rules keep it honest:

    1. One question at a time. Bundled questions get bundled, vague answers.
    2. Always offer a recommendation. Reacting to a concrete proposal is faster and more revealing than filling a blank page. Disagreement with the recommendation is where the real requirements surface.
    3. Walk the frontier. At any moment, the frontier is the set of open questions whose parent questions are answered. Ask from the frontier only. "Which wire format?" means nothing until "do we build our own server?" is settled.

    The twelve decisions

    Each entry gives the alternative that lost and the observation that would reopen it. Open one to see the reasoning.

    1. D1Why build storage and networking at all?learning-driven custom build

      Rejected adopting DuckDB, ClickHouse or kdb+.

      Why The goal is to learn how these systems work, and score is a learning project. Production-grade storage is not a requirement yet.

      Reopen if a real user needs durability guarantees before the store has a crash-recovery story.

    2. D2gRPC or a custom TCP engine?custom TCP now, gRPC in Phase 11

      Rejected gRPC/Protobuf as the first network layer.

      Why gRPC hides sockets, framing and concurrency, which are the things to learn. It stays on the roadmap as a compatibility facade over the same abstractions.

      Reopen if a non-C++ client needs typed stubs before Phase 8 lands.

    3. D3Which concurrency model?v1 threads → v2 epoll → v3 io_uring

      Rejected picking one model.

      Why Each model teaches something different, and building them in order makes the cost of the previous one visible. io_uring is an optional stretch goal.

      Reopen if v1 can't pass its loopback tests; fix the simple model before adding a faster one.

    4. D4How does a Linux-only API build on a Mac?platform-agnostic EventLoop

      Rejected Linux-only development in a VM or container.

      Why macOS offers kqueue, not epoll. If Server and Connection depend only on an EventLoop interface, v1 builds everywhere and the epoll backend sits behind a Linux-only CMake guard (Phase 4).

      Reopen if the interface needs per-backend #ifdefs inside Server.

    5. D5What goes on the wire first?4-byte BE length + JSON, behind FrameCodec

      Rejected a custom binary format first; newline-delimited JSON.

      Why JSON is debuggable and nlohmann_json is already a dependency. The FrameCodec interface means the binary codec in Phase 8 only replaces the codec.

      Reopen if profiling shows JSON parsing dominating request latency.

    6. D6Embedded database or hand-built store?custom columnar store, daily OHLCV

      Rejected SQLite, DuckDB.

      Why Same reason as D1. Restricting v1 to daily bars keeps the data small and the layout simple; intraday data is deferred.

      Reopen if intraday data becomes a requirement; tick volumes change every layout decision.

    7. D7How do the two data paths meet?one IngestionSource interface

      Rejected separate loaders per source.

      Why yfinance and the GBM generator differ only in where bars come from. One interface lets tests use the mock source and production use yfinance with no other change.

      Reopen if a source needs a capability the interface can't express, such as streaming.

    8. D8Who uses this?pre-trade risk checks + backtesting

      Rejected a live streaming dashboard.

      Why Both users issue requests and wait for an answer over historical data. That favours request/response framing and range scans over a pub/sub design.

      Reopen if someone needs push updates.

    9. D9Should VaR/CVaR wait for its roadmap phase?real historical VaR/CVaR now

      Rejected leaving it as a roadmap item.

      Why It is small, fully specified, and the metric the users actually ask for.

      Reopen if backtests show the estimator is miscalibrated (see Chapter 6, Q6).

    10. D10New repo, new binary, or the existing core?score::db + score::net in score_core

      Rejected a separate service repository.

      Why The risk math, the store and the server share types and the exception hierarchy. One library keeps the build simple.

      Reopen if the net module's dependencies (liburing, later gRPC) start burdening users who only want the math.

    11. D11How much gets built this pass?interfaces + throwing stubs

      Rejected building v1 of everything at once.

      Why Headers with full signatures let the design be reviewed before any behaviour exists. Every stub throws score::NotImplementedError, so a premature call fails loudly. VaR/CVaR is the exception.

    Chapter 02 · score::net

    TCP is a byte stream, not a message queue

    Before Server::listen can do anything, it has to walk the socket lifecycle. And before Connection can read a request, it has to accept that TCP will hand it bytes in whatever chunks it likes.

    Learning goals
    • Trace socket → bind → listen → accept on the server and socket → connect on the client, including the three-way handshake.
    • Explain the listen backlog and the accept queue.
    • Show, with a real loopback trace, why one write can arrive as several reads and why two writes can arrive as one.
    • Map each step onto Server, Connection and EventLoop.

    The lifecycle

    A server socket is a factory for connections. socket() creates an endpoint, bind() attaches it to an address and port, and listen() marks it passive: the kernel will now complete TCP handshakes on its behalf. Each completed handshake waits in an accept queue until the program calls accept(), which returns a new file descriptor for that one connection. The listening socket never carries data.

    Backlog and the accept queue

    The backlog argument to listen() bounds how many completed connections may wait for accept(). On Linux since 2.2 it limits the queue of fully established connections, and the kernel silently caps it at net.core.somaxconn. On this Mac, sysctl kern.ipc.somaxconn reports 128 verified. When the queue is full, new handshakes are not completed, and clients see slow or failed connects. A server that calls accept() too rarely has a backlog problem no matter how fast it is otherwise.

    Why messages must be framed

    TCP promises that bytes arrive in order, exactly once, or the connection fails. It promises nothing about boundaries. A read() returns whatever is in the receive buffer, from 1 byte up to the size you asked for. Segment sizes, Nagle's algorithm (RFC 896), delayed ACKs and scheduler timing all change where the chunks fall. Two consequences follow:

    • One write can arrive as many reads. The receiver must buffer until it has a whole message.
    • Many writes can arrive as one read. The receiver must be able to pull several messages out of one buffer, and keep the leftover bytes of a partial one.

    Both happen on loopback, where you might expect neither. This Python script sends the 44-byte frame from Chapter 4 once in three pieces (with short pauses and TCP_NODELAY), then sends two frames in a single sendall:

    A read() that returns 0 means the peer closed its sending side (EOF). On a non-blocking socket, -1 with errno == EAGAIN means "nothing to read right now", which is the normal state of an idle connection in an event loop.

    Engineering questions

    1. Server::listen(std::uint16_t port) takes no bind address and no backlog. Choose defaults for both and justify them. What should happen when port is 0?

      Hint

      Port 0 asks the kernel for an ephemeral port, which is what loopback tests want. They then need getsockname() to discover it. Is there a method on Server that could return it?

    2. read() returns 0 on a connection. Which object notices, which object destroys the Connection, and in what order must unregister, close and destruction happen?

      Hint

      Ownership lives in Server::connections_, a vector of unique_ptr. A callback that destroys the object it is running inside is a use-after-free waiting to happen.

    3. On a non-blocking socket write() accepts 17 of 44 bytes. Design Connection::send using IoEvent::kWritable. When do you register for writability, and when do you stop?

      Hint

      An idle socket is almost always writable. If you stay registered, a level-triggered loop wakes you constantly. Register only while an outbound buffer is non-empty.

    4. The peer has closed and you write to the socket. What does the process receive by default, and how do you prevent it on Linux and on macOS?

      Hint

      Look up SIGPIPE, the MSG_NOSIGNAL flag to send(), and the SO_NOSIGPIPE socket option. They are not available on the same platforms.

    5. using SocketHandle = int; encodes a POSIX assumption. What breaks on Windows, and how would you change the type without touching every caller?

      Hint

      Winsock's SOCKET is an unsigned pointer-sized integer, and its invalid value is not -1.

    One thread per socket, or one loop for all of them

    The roadmap builds three backends for one interface: blocking threads, epoll, and io_uring. This chapter gives you the cost model that tells them apart and the patterns, reactor and proactor, that each one implements.

    Learning goals
    • Estimate the memory and scheduling cost of thread-per-connection for a given connection count.
    • Explain why select/poll cost grows with every watched descriptor and epoll/kqueue cost grows with ready ones.
    • Distinguish the reactor (readiness) and proactor (completion) patterns, and place io_uring's two rings.
    • Map each backend onto register_io, unregister, run and stop.
    include/score/net/event_loop.hpprepo · verbatim · whole file
    #pragma once

#include <functional>

namespace score::net {

using SocketHandle = int;

enum class IoEvent { kReadable, kWritable };

using IoCallback = std::function<void(SocketHandle, IoEvent)>;

/// Platform-agnostic reactor interface. Server/Connection depend only on
/// this, never on a concrete backend, so the concurrency model (blocking
/// thread-per-connection, epoll, io_uring, ...) can be swapped without
/// touching them.
class EventLoop {
public:
    virtual ~EventLoop() = default;

    /// Registers `cb` to be invoked when `fd` becomes ready for `event`.
    virtual void register_io(SocketHandle fd, IoEvent event, IoCallback cb) = 0;

    /// Stops watching `fd`.
    virtual void unregister(SocketHandle fd) = 0;

    /// Runs the loop until stop() is called. Blocks the calling thread.
    virtual void run() = 0;

    /// Signals run() to return.
    virtual void stop() = 0;
};

}  // namespace score::net

    Model 1: a thread per connection

    The simplest server accepts a connection and hands it to a thread that blocks in read(). The code reads top to bottom and the kernel scheduler does the multiplexing. The costs scale with the connection count N:

    Mstack=N·S

    where S is the stack reserved per thread. That is virtual address space; physical pages are committed only as the stack is touched (16 KiB pages on this machine, hw.pagesize). Measured on this Mac:

    On Linux, glibc takes the default thread stack from RLIMIT_STACK (ulimit -s), which is 8 MiB on most distributions. At 10,000 connections that is 78 GiB of reserved address space. That fits in a 64-bit address space, so the binding limits are usually elsewhere: per-process thread caps such as macOS's 9,216, scheduler overhead when thousands of threads wake, and cache pollution from switching between them.

    Model 2: readiness multiplexing

    The alternative keeps every socket non-blocking and asks the kernel one question: which of these descriptors can I use without blocking? One thread then serves all of them.

    • select (4.2BSD) passes bitmaps of up to FD_SETSIZE descriptors on every call. The kernel scans them all, and the caller scans the result again.
    • poll removes the fixed limit with an array of pollfd structs, but still copies and scans the whole array per call.
    • epoll (Linux 2.5.44, 2002) and kqueue (FreeBSD 4.1, 2000; also macOS) keep the interest set inside the kernel. You register a descriptor once; each wait returns only the descriptors that are ready.

    If N descriptors are watched and r are ready, the work per wakeup is

    Wpoll∈Θ(N)Wepoll∈Θ(r)

    With 10,000 mostly idle connections and 50 ready, that is the difference between examining 10,000 entries and examining 50, on every turn of the loop.

    Reactor and proactor

    Douglas Schmidt named the pattern behind every readiness loop the Reactor: a synchronous event demultiplexer (epoll_wait, kevent) waits for readiness, and a dispatcher calls the handler registered for that descriptor. The handler then performs the I/O itself, knowing it will not block. The Proactor inverts this: the program starts an asynchronous operation with a buffer, the operating system performs the I/O, and the dispatcher delivers a completion. Windows I/O completion ports and io_uring are proactor-shaped.

    io_uring: two rings in shared memory

    io_uring, by Jens Axboe, merged in Linux 5.1 (2019). The application and kernel share two ring buffers mapped into both address spaces. The application writes submission queue entries (SQEs) at the tail of the SQ ring; the kernel consumes them from the head, performs the operations, and writes completion queue entries (CQEs) to the CQ ring. One io_uring_enter system call can submit many operations and wait for many completions, and with SQPOLL a kernel thread polls the SQ so submission needs no system call at all.

    History · the C10K problem

    In 1999 Dan Kegel published "The C10K problem", asking how one server could handle ten thousand simultaneous clients. Apache's prefork model, one process per connection, was the common answer of the day and hit exactly the costs above. Kegel's page surveyed the alternatives that followed: kqueue (Jonathan Lemon, FreeBSD, paper at USENIX 2001), epoll (Linux 2.5.44), and event-driven servers such as nginx, first released by Igor Sysoev in 2004, which runs a few worker processes that each drive one event loop. io_uring (2019) is the latest step in the same line.

    Engineering questions

    1. A caller does register_io(fd, kReadable, cb1) then register_io(fd, kWritable, cb2). Does the second call add to or replace the first? Write the contract, then check whether epoll and kqueue can implement it directly.

      Hint

      epoll keys registrations by descriptor, and a second EPOLL_CTL_ADD for the same fd fails with EEXIST. kqueue keys them by the pair (ident, filter).

    2. Does the interface promise level-triggered or edge-triggered callbacks? If the epoll backend uses EPOLLET, what must every callback do that a level-triggered callback may skip?

      Hint

      With edge triggering you are told once that data arrived. If you leave bytes in the buffer, nobody will tell you again.

    3. stop() is called from another thread while run() sleeps in epoll_wait with no timeout. How does run() wake up? Is stop() required to be thread-safe by the current comment?

      Hint

      Read the doc comment on stop() again. Then look up the self-pipe trick and eventfd.

    4. Using the bench, find the connection count where v1 fails on macOS. Is it memory or something else? What would you put in the v1 test suite to make this limit visible?

      Hint

      Compare kern.num_taskthreads with the reserved-stack figure at the same N.

    5. IoCallback is a std::function. When can constructing one allocate, and does that matter at 10,000 registrations per second?

      Hint

      Look up small-buffer optimisation in your standard library. A lambda that captures this and an fd is small; one that captures a std::string may not be.

    6. Sketch a proactor-style method for EventLoop that io_uring could implement natively. Who owns the buffer between submission and completion, and how do you cancel safely?

      Hint

      Something like async_read(fd, std::span<std::byte>, completion). Cancellation is itself an asynchronous operation in io_uring.

    Forty-four bytes, one frame

    Chapter 2 showed that TCP hands you a stream. A framing protocol puts the boundaries back. The v1 protocol is the simplest one that works: four bytes of length, then that many bytes of JSON.

    Learning goals
    • Encode a real request by hand, byte by byte, including the big-endian length prefix.
    • Write a feed/try_decode decoder that survives split and coalesced reads.
    • Defend against a malicious length prefix before allocating anything.
    • See why a binary codec in Phase 8 changes only the codec, and where that promise leaks.

    nlohmann::json payload;

/// Wire-format abstraction: encodes a Frame to bytes and incrementally
/// decodes bytes back into Frames. Connection/Server hold a FrameCodec by
/// interface, so swapping the v1 JSON codec for a hand-rolled binary codec
/// later only touches the codec implementation.

    std::vector<std::uint8_t> encode(const Frame& f) const {
        const std::string body = f.payload.dump();
        const auto n = static_cast<std::uint32_t>(body.size());
        std::vector<std::uint8_t> out{
            static_cast<std::uint8_t>(n >> 24), static_cast<std::uint8_t>(n >> 16),
            static_cast<std::uint8_t>(n >> 8),  static_cast<std::uint8_t>(n)};
        out.insert(out.end(), body.begin(), body.end());
        return out;
    }
    void feed(const std::uint8_t* data, std::size_t len) { buffer_.insert(buffer_.end(), data, data + len); }
    std::optional<Frame> try_decode() {
        if (buffer_.size() < 4) return std::nullopt;                       // need the whole prefix
        const std::uint32_t n = (std::uint32_t{buffer_[0]} << 24) | (std::uint32_t{buffer_[1]} << 16) |
                                (std::uint32_t{buffer_[2]} << 8)  |  std::uint32_t{buffer_[3]};
        if (n > kMaxFrame) throw std::length_error("frame too large");   // reject before allocating
        if (buffer_.size() < 4 + n) return std::nullopt;                   // need the whole payload
        Frame f{nlohmann::json::parse(buffer_.begin() + 4, buffer_.begin() + 4 + n)};
        buffer_.erase(buffer_.begin(), buffer_.begin() + 4 + n);           // keep any trailing bytes
        return f;
    }
    std::size_t buffered() const { return buffer_.size(); }
private:

      Defence · the malicious prefix

      The prefix is attacker-controlled. 7f ff ff ff claims a 2,147,483,647-byte payload and ff ff ff ff claims 4,294,967,295 verified. A decoder that calls buffer_.reserve(n) on trust, or simply waits for n bytes, can be pushed into a 2 GiB allocation or into holding a connection open forever. The sketch rejects any n above kMaxFrame = 1 MiB as soon as the four prefix bytes are in. A cap does not stop a peer that sends a legal 1 MiB header and then trickles one byte a minute; that needs a per-connection read deadline.

      The definitions

      Let X be the one-period return with distribution function FX, and α the confidence level (0.95, 0.99). VaR is the loss that is exceeded with probability at most 1−α:

      VaRα(X)=−inf{x:FX(x)>1−α}

      Expected Shortfall averages VaR over every confidence level beyond α, which for a continuous distribution equals the mean loss in the tail:

      ESα(X)=11−α∫α1VaRu(X)du

      Historical simulation replaces FX with the empirical distribution of the last n observed returns. No distribution is assumed, which is its strength. It also assumes the next day is drawn from the same window, which is its weakness: a window of calm years contains no crash.

// quantile and its mean is CVaR.
struct HistoricalTail {
    std::vector<double> sorted_returns;
    std::size_t          tail_index;
};

HistoricalTail historical_tail(const std::vector<double>& returns, double confidence_level, const char* caller) {
    if (returns.empty()) { throw score::EmptySeriesError(std::string(caller) + ": returns series is empty"); }

    if (confidence_level <= 0.0 || confidence_level >= 1.0) {
        throw score::DomainError(std::string(caller) +
                                  ": confidence_level must be in (0, 1), got " + std::to_string(confidence_level));
    }

    // A tiny epsilon absorbs binary floating-point error in (1 - confidence_level)
    // (e.g. 1.0 - 0.90 == 0.09999999999999998), which would otherwise truncate
    // an exact boundary like n=10, confidence_level=0.90 down to tail_index 0.
    constexpr double  kEpsilon     = 1e-9;
    const double      tail_fraction = 1.0 - confidence_level;
    const std::size_t tail_index =
        static_cast<std::size_t>(tail_fraction * static_cast<double>(returns.size()) + kEpsilon);
    if (tail_index == 0) {
        throw score::DomainError(std::string(caller) + ": not enough returns (" + std::to_string(returns.size()) +
                                  ") to resolve the " + std::to_string(confidence_level) + " confidence quantile");
    }

    std::vector<double> sorted_returns = returns;
    std::sort(sorted_returns.begin(), sorted_returns.end());
    return HistoricalTail{std::move(sorted_returns), tail_index};
}

      Each loan alone defaults less often than 5%, so each has VaR 0. Together, the chance that at least one defaults is 1−0.962=0.0784, which is above 5%, so the portfolio's VaR is 100.       Regulation followed

      The 1996 Basel market-risk amendment set capital from a 10-day, 99% VaR. After 2008, Basel 2.5 (2009) added a "stressed VaR" computed over a crisis window, and the Fundamental Review of the Trading Book (BCBS, January 2016, revised January 2019) replaced VaR with Expected Shortfall at 97.5%. The level was chosen so that, for normally distributed returns, the two numbers roughly agree:

      VaR0.99=2.326σES0.975=φ(z0.975)0.025σ=2.338σ

      verified (Python statistics.NormalDist). For fat-tailed returns ES grows faster than VaR, which is the point.

      History · VaR's rise and its limits

      J.P. Morgan published its RiskMetrics methodology in 1994 and made VaR an industry vocabulary. In 1998 Long-Term Capital Management, a highly leveraged fund whose models were calibrated on recent history, lost most of its capital in a few months after Russia's default; the Federal Reserve Bank of New York organised a recapitalisation of about $3.6 billion by a consortium of banks. In 2008, many VaR models fed by calm pre-crisis windows understated the risk of the assets that then failed. Both episodes are about the window, not the arithmetic, and both are why the questions below matter.

      Why 1.0 − 0.90 is not 0.1, and what 1e-9 fixes

      The first version of historical_tail threw at n=10, c=0.90, where ten returns should give a one-element tail. Every step of the arithmetic was correct. The error was in the number 0.9 itself.

      Learning goals
      • Read an IEEE 754 binary64 value from its sign, exponent and fraction bits, and compute its exact decimal value.
      • Show that 1.0 - 0.90 and the multiplication by 10 are both exact, and locate the error.
      • Explain how truncation turns a tiny representation error into an off-by-one.
      • Find where the 1e-9 fix stops working, and compare it with integer and relative-tolerance alternatives.

      binary64 in one paragraph

      A double is 64 bits: 1 sign bit s, 11 exponent bits e, and 52 fraction bits f. For normal numbers its value is

      x=(−1)s·(1+f252)·2e−1023

      Every double is a fraction with a power-of-two denominator. 1/10 is not, because 10 has a factor of 5, so 0.1 and 0.9 are stored as the nearest such fraction. Those nearest values are verified:

      Where the error enters

      Sterbenz's lemma says that if y/2≤x≤2y, then x−y is computed exactly. 1.0 and 0.9 qualify, so 1.0 - 0.9 introduces no rounding at all. The multiplication by 10 is also exact here, since 1−2−52 is representable verified. The only inexact step was turning the decimal literal 0.90 into binary: it is stored about 2.2×10−17 too high, so 1−c comes out that much too low, and

      ⌊0.99999999999999977795…⌋=0instead of1

      Truncation is the amplifier. Rounding would have absorbed an error of one part in 1016; static_cast<std::size_t> turns it into a whole observation. Of the fifty levels 0.50, 0.51, …, 0.99 at n=10, exactly two are affected without the epsilon verified: 0.80 (tail 1 instead of 2, so VaR 0.05 instead of 0.04) and 0.90 (tail 0, so a throw instead of 0.05).

      How good is the epsilon?

      The fix adds ε=10−9 before truncating. An exhaustive check compared it with exact integer arithmetic for every confidence level with at most four decimals (0.0001 to 0.9999) and every n from 1 to 200,000 verified:

      FormulaPairs checkedWrong tail_index
      floor((1 − c)·n), the bug1,999,800,000391,760
      floor((1 − c)·n + 1e-9), the repo1,999,800,0000

      So for realistic inputs the fix is correct. It has two limits, both verified:

      • It is absolute, but the error is relative. The representation error of 1−c is multiplied by n. At n=108 and c=0.80 the repo formula gives 19,999,999 instead of 20,000,000; at n=109 and c=0.90, 99,999,999 instead of 100,000,000. Nobody has 108 daily bars, but intraday ticks get there.
      • It can round up a value that is really below an integer. For c=0.90000000001 and n=10 the true product is 0.9999999999, whose floor is 0, but adding 10−9 gives 1.

      Alternatives

      Integer basis points. If the confidence arrives as an integer number of basis points, every step is exact and there is nothing to tune. This also matches the binary wire format from Chapter 4.

      sketches.cpp · tailbpsketch · not in repo · compiled & tested
      // Confidence carried as integer basis points (9500 == 95.00%).
// Every step is exact integer arithmetic: no epsilon, no rounding mode.
std::size_t tail_index_bp(std::size_t n, std::uint32_t confidence_bp) {
    if (confidence_bp == 0 || confidence_bp >= 10'000) {
        throw std::domain_error("confidence_bp must be in (0, 10000)");
    }
    return n * (10'000 - confidence_bp) / 10'000;  // floor, exactly
}

      Relative tolerance. If the API must take a double, snap to the nearest integer only when within a tolerance proportional to the magnitude.

      sketches.cpp · tailrelsketch · not in repo · compiled & tested
      // Snap to the nearest integer only when x is within a *relative*
// tolerance of it; otherwise truncate as before.
std::size_t tail_index_rel(std::size_t n, double confidence_level) {
    const double x = (1.0 - confidence_level) * static_cast<double>(n);
    const double r = std::round(x);
    const double tol = 1e-12 * std::max(1.0, std::abs(x));
    return static_cast<std::size_t>(std::abs(x - r) <= tol ? r : std::floor(x));
}

      Three historical failures

      1991 · Patriot missile, Dhahran

      On 25 February 1991 a Patriot battery in Dhahran, Saudi Arabia, failed to intercept an incoming Scud, which struck a barracks and killed 28 American soldiers. The GAO's 1992 report traced it to time-keeping. The system counted time in tenths of a second and converted to seconds by multiplying by 1/10 held in a 24-bit fixed-point register. That constant, 0.00011001100110011001100 in binary (1/10 chopped after 23 fractional bits), is short by about 9.5×10−8 per tick. The battery had been running for about 100 hours. Same arithmetic, drift by uptime verified:

      UptimeClock errorScud travel in that time (≈1,676 m/s)
      1 h0.0034 s6 m
      8 h0.0275 s46 m
      20 h0.0687 s115 m
      48 h0.1648 s276 m
      72 h0.2472 s414 m
      100 h0.3433 s575 m

      Lesson for score: a representation error of one part in ten million is harmless once and fatal when multiplied by a large count. That is the n-scaling limit of the epsilon above.

      1982–83 · Vancouver Stock Exchange index

      The exchange launched an index at 1000.000 in January 1982 and recomputed it after every trade, keeping three decimals by truncating rather than rounding. Each truncation dropped on average half a unit in the last place, 0.0005 points, always downwards. Over about 22 months of frequent updates the published index fell to roughly half its correctly computed value before the error was found and the index recomputed in November 1983.

      Lesson for score: a biased rounding mode compounds. static_cast<std::size_t> is truncation; it is fine for a count only when the input is known to be exact.

      1996 · Ariane 5 Flight 501

      About 40 seconds after launch on 4 June 1996, Ariane 5's first flight broke up. The inquiry board led by Jacques-Louis Lions found that inertial reference software reused from Ariane 4 converted a 64-bit floating-point value (horizontal bias) to a 16-bit signed integer. Ariane 5's faster trajectory produced a value too large for 16 bits, the conversion raised an operand error, and both reference units shut down.

      Lesson for score: a narrowing conversion is a range assumption. historical_tail converts a double to std::size_t; what happens if the double is negative or NaN? The (0, 1) check on confidence_level runs first. Does it reject NaN? (Every comparison with NaN is false.)
